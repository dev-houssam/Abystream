# Authentication

Abystream provides authentication utilities based on JSON Web Tokens
(JWT).

The authentication implementation is provided by the
`framework/auth` module and uses the native cryptographic functions
provided by the Abystream web shim.

---

## 1. Overview

The authentication module provides the operations required to create
and verify JWT tokens.

```text
Application
     │
     ▼
Authentication module
     │
     ├── Encode JWT
     │
     ├── Sign JWT
     │
     └── Verify JWT
            │
            ▼
        Authenticated
        application
```

The current implementation uses the HMAC SHA-256 algorithm, commonly
identified as:

```text
HS256
```

---

## 2. Authentication module

The implementation is located in:

```text
framework/
└── auth/
    ├── auth.mabc
    └── conf.toml
```

The module depends on:

```text
core
native webshim
```

The cryptographic operations are provided by native functions exposed
through the web shim.

---

## 3. JSON Web Token

A JWT is composed of three Base64URL-encoded sections:

```text
header.payload.signature
```

For example:

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
eyJ1c2VyX2lkIjoxfQ
.
signature
```

The three components are:

```text
Header
Payload
Signature
```

Abystream constructs and verifies these components through the
authentication module.

---

## 4. JWT header

The module provides:

```text
jwt_header_b64()
```

This function returns the Base64URL representation of the JWT header.

The header represented by the implementation is:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

The header identifies:

```text
alg = HS256
typ = JWT
```

---

## 5. Base64URL encoding

The authentication module provides:

```text
jwt_b64url(str s)
```

This function uses the native:

```text
matlabc_b64url
```

operation.

The purpose is to encode JWT components using the Base64URL
representation required by the JWT format.

---

## 6. JWT signing

The signature is generated by:

```text
jwt_sign(str message, str secret)
```

The function uses the native cryptographic operation:

```text
matlabc_hmac_sha256_b64url
```

Conceptually:

```text
message
   │
   ▼
HMAC-SHA256
   │
   │ secret
   ▼
Base64URL signature
```

The secret is therefore used to authenticate the token's contents.

---

## 7. JWT encoding

The main token creation function is:

```text
jwt_encode(str payload_json, str secret)
```

The function creates the three JWT components:

```text
header
payload
signature
```

and combines them using the JWT structure:

```text
header.payload.signature
```

The process is:

```text
Payload JSON
     │
     ▼
Base64URL payload
     │
     ├──────────────┐
     │              │
     ▼              ▼
Header          Payload
     │              │
     └──────┬───────┘
            ▼
     header.payload
            │
            ▼
       HMAC-SHA256
            │
            │ secret
            ▼
        Signature
            │
            ▼
header.payload.signature
```

---

## 8. Example payload

An application can construct a JSON payload containing information
required by its authentication system.

For example:

```json
{
  "user_id": 42
}
```

The authentication module does not define the application's user
model.

The application decides which claims are appropriate for its own
authentication system.

---

## 9. JWT verification

The verification function is:

```text
jwt_verify(str token, str secret)
```

Verification checks that the token has the expected JWT structure and
that its signature matches the signature generated from the supplied
secret.

Conceptually:

```text
JWT
 │
 ├── Header
 ├── Payload
 └── Signature
       │
       ▼
Recompute signature
       │
       │ secret
       ▼
Compare signatures
       │
       ├── Match
       │     │
       │     ▼
       │  Valid token
       │
       └── Different
             │
             ▼
         Invalid token
```

---

## 10. Token structure validation

Before verification, the implementation checks the structure of the
token.

The current implementation expects two `.` separators:

```text
header.payload.signature
```

A token that does not contain the expected JWT structure is rejected.

---

## 11. Payload extraction

The module provides:

```text
jwt_payload_b64(str token)
```

This function extracts the payload section from a JWT.

For:

```text
header.payload.signature
```

the function returns:

```text
payload
```

The payload can then be Base64URL-decoded.

---

## 12. Base64URL decoding

The module also provides:

```text
jwt_b64url_decode()
```

This operation converts the Base64URL representation back into the
corresponding data.

The general flow is:

```text
JWT
 │
 ▼
Payload section
 │
 ▼
Base64URL decoding
 │
 ▼
Payload JSON
```

This allows the application to access the information contained in a
verified JWT payload.

---

## 13. JWT parsing helpers

The authentication implementation includes:

```text
jwt_find_char()
```

This helper is used to locate separators while processing the JWT
string.

Together with the payload extraction and decoding functions, it
provides the operations necessary to process the token structure.

---

## 14. Authentication flow

A typical authentication flow can be represented as:

```text
Client
  │
  │ Login request
  ▼
Application
  │
  ├── Verify credentials
  │
  ▼
Create JWT
  │
  ▼
Return token
  │
  ▼
Client
```

The client can then provide the token when accessing protected
resources.

---

## 15. Authenticated request

A subsequent request can contain the authentication token.

Conceptually:

```text
Client
  │
  │ Request + JWT
  ▼
Abystream
  │
  ▼
Extract token
  │
  ▼
jwt_verify()
  │
  ├── Valid
  │     │
  │     ▼
  │   Handler
  │
  └── Invalid
        │
        ▼
     Reject
```

The exact location and transport of the token are determined by the
application.

## 16. Authentication and middleware

Authentication can be combined with Abystream middleware.

The conceptual request pipeline becomes:

```text
HTTP Request
     │
     ▼
Middleware
     │
     ▼
Extract authentication data
     │
     ▼
jwt_verify()
     │
     ├── Valid ─────► Router / Handler
     │
     └── Invalid ───► Authentication response
```

The middleware system is provided by:

```text
framework/
└── middleware/
    ├── middleware.mabc
    └── conf.toml
```

The authentication module itself provides the JWT operations, while
the application can decide how and where those operations are used.

## 17. Authentication and routing

Authentication can be applied to specific routes.

For example:

```text
GET /login
GET /public
GET /dashboard
GET /profile
```

The application may leave some routes public while requiring
authentication for others.

Conceptually:

```text
Request
  │
  ▼
Router
  │
  ├── Public route
  │      │
  │      ▼
  │    Handler
  │
  └── Protected route
         │
         ▼
      Middleware
         │
         ▼
      jwt_verify()
         │
         ▼
       Handler
```

See [Routing](routing.md).

## 19. Secret management

JWT signing and verification require a secret.

The secret is supplied to:

```text
jwt_encode()
```

and:

```text
jwt_verify()
```

The same secret must be available to the components responsible for
creating and verifying tokens.

The secret should therefore be managed as application configuration
rather than being embedded directly into application source code.

For example:

```text
Application configuration
        │
        ▼
Authentication secret
        │
        ├──────────────► jwt_encode()
        │
        └──────────────► jwt_verify()
```

## 20. Native cryptography

The high-level authentication module delegates cryptographic
operations to the native web shim.

The architecture is:

```text
MATL-ABC Application
        │
        ▼
framework/auth/auth.mabc
        │
        ▼
Native web shim
        │
        ▼
HMAC-SHA256
        │
        ▼
Base64URL signature
```

The native operation used for signing is:

```text
matlabc_hmac_sha256_b64url
```

This keeps the cryptographic primitive outside the high-level JWT
implementation.

## 24. Security boundary

The authentication module is responsible for JWT-related operations,
but it does not define the complete security policy of an
application.

The application remains responsible for decisions such as:

* how users are authenticated
* how credentials are validated
* which routes require authentication
* which claims are placed in a token
* how authentication failures are handled
* how secrets are supplied through configuration

The framework provides the underlying JWT mechanisms used by these
application-level decisions.

